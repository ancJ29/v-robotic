# P6 report: the Lightsail box, as scripts

Plain words. Each item ends in one question you can answer yes or no. Nothing has been pushed.

**The most important fact: none of this has ever run against a real box.** I cannot reach AWS from my sandbox, so I created nothing and tested nothing on Ubuntu. What I could test (the text of every file, the secret-making code, the refusals, a dry run) passed. Everything past that is written from what S0b did on the real box, with some new parts around it. Your first run is the first real test. If it fails, the log says which step, and the note `docs/conventions/box.md` lists the four most likely causes.

## What now exists

1. **A folder of box scripts in the repository (`ops/box/`).** Swap file, Node, a locked-down `strapi` account, the unpacked app, a secrets file made on the box, Strapi kept alive by the system's own service manager and restarted on reboot, Caddy in front with https, the first admin account, ssh by key only. Every setting (names, ports, folders, domain) is a variable with a default.
2. **One script you paste to create the box** (`/Users/hau/projects/freelance/v-robotic/one-off/20261109-0957-p6-box.sh`): makes the box, a fixed address, the firewall, uploads the app, runs the scripts, then **restarts the box on purpose** to prove it comes back by itself.
3. **One script you paste to destroy it** (`/Users/hau/projects/freelance/v-robotic/one-off/20261109-0959-p6-teardown.sh`): deletes the box, releases the fixed address, deletes the key, removes the local key folder, and checks with AWS that nothing named after the box is left.
4. **The secrets rule.** The throwaway local passwords and keys can never reach the box: four separate checks refuse or remove them. The real keys and the admin password are made on the box, kept in files only the box's root account can read, and never printed anywhere, including this report.
5. **Plan lines corrected, open items 2 and 3 closed.** The plan said Lightsail got the artifact in S0a (it does not; P6 does) and that the box would install packages (it unpacks instead). The architecture drawing said pm2; it is the system's service manager.
6. **One small change to the CMS settings** (`cms/config/server.ts`): two switches that are off by default, which the box turns on so the admin login cookie is marked secure behind https.

## Cost

About **5 US dollars a month, which is about 17 US cents a day**, billed by the hour from creation until the teardown confirms deletion. A four-hour test day costs about 3 cents. The fixed address is free while attached and is released by the teardown. The 1 GB plan, if ever needed, is about 7 dollars a month.

## What would still bill after teardown

Nothing these scripts make. Only things they do not touch: a snapshot you took by hand (the teardown lists it loudly and deletes it only if you add `DELETE_SNAPSHOTS=1`), some other unattached fixed address, a domain, anything in another region.

## What you do in your own console and terminal

1. Push the `p6-box` branch and let the CMS build on GitHub finish (the box needs an app built after my settings change; the script refuses an older one). Note the run number.
2. Make sure AWS is signed in on your Mac, then paste the create script with your box name, region, your email and the run number. It prints its own plan and waits 15 seconds before creating anything.
3. Open the https address it prints, read the admin password with the one command it prints (that shows the password in your terminal, your choice), log in, and change the password.
4. At the end of the day, paste the teardown script with the same name and region.

## Questions

1. **Is a service manager (systemd) instead of pm2 acceptable?** Yes: it is what S0b measured and needs no extra program on a tiny box; no: say why and I will rework the service step.
2. **Is the app unpacked on the box (never installed there) the right way?** Yes: nothing is downloaded or built on 512 MB; no: the box would install about 1,250 packages itself.
3. **Is an address like `203-0-113-7.sslip.io` acceptable for testing until a real domain exists?** Yes: free and automatic; no: give me a domain and its name is set in one variable. (The free name is shared with the whole internet and its certificates have public limits, so repeated daily boxes may sometimes fail to get one.)
4. **Is it right that the R2 image storage and the client's own login are not part of this piece?** Yes: they need the bucket's key and the client's details, which are yours to give; no: tell me which comes first.
5. **Are you happy that the create script restarts the box once to prove it survives a reboot (costs about 3 extra minutes)?** Yes: keep it; no: set `REBOOT_TEST=0`, and the survive-a-reboot claim stays unproven.
6. **Is the teardown's rule right: it keeps any hand-made snapshot and only warns, unless you ask it to delete?** Yes: your data is never deleted by surprise; no: it would delete them too.
