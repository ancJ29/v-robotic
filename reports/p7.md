## What now exists

1. **Publish to live site.** When the client presses Publish in Strapi, Strapi tells a small relay on your website (`/api/rebuild`); the relay checks a password and asks GitHub to run the existing deploy, set to read from Strapi. About two to four minutes later the change is live. A manual deploy from the Actions tab still builds from the committed files and does not need the box. *Question: do you accept one deploy workflow with a switch, rather than a second workflow for Strapi?*
2. **A dead box cannot break the live site.** If the box does not answer, the run stops before building and the site keeps what it had. *Question: do you accept that a failed publish is only visible in the Actions tab, with no message to the client?*
3. **The image problem (open item 17) is closed.** Built against a real local Strapi, the pages first pointed every picture at `127.0.0.1` (144 times, which nobody can open). With the box's public address set, all 144 point at the public address and none local. The deploy now fails if a local picture address ever gets into a page. **The catch:** pictures are still served by the box, so while the box is down the pages work but their pictures do not. Copying the pictures into each build would remove that; I did not build it. *Question: do you accept pictures living on the box for now?*
4. **A nightly backup on the box.** Every night at 03:30 (UTC) it takes a safe copy of the content database even while the client is editing, checks the copy, and keeps the newest 14. It also keeps one mirror of the uploaded pictures. *Question: do you accept 14 nights as the history?*
5. **What the backup costs in space.** Today the database is 2.2 MB and the pictures 0.4 MB, so 14 nights are about 15 MB or less. With real product photos the picture mirror will dominate (it holds one copy, not 14). The script refuses to run, and deletes nothing, if the disk has less than 500 MB free. The 512 MB box has a small disk, so look at it once the real photos are in. *Question: do you accept this and check the disk once after the photos are uploaded?*
6. **If the box dies between backups.** The backups are on the same box, so if the box is deleted or its disk fails they die with it. You would lose the edits since the last copy that survived, and the site itself would be fine (it is static, only its pictures would break). Two cures: Lightsail's automatic snapshots (a setting you click, about 5 US cents per GB-month) or a copy sent elsewhere (needs a key from you). I recommend the snapshots. *Question: will you switch on Lightsail automatic snapshots?*
7. **The proofs I could run.** The relay logic (6 tests: right call, wrong password refused, test button starts nothing, GitHub refusing is reported); both workflows pass the workflow checker; the site builds from Strapi (43 pages) and from the seed with Strapi stopped (43 pages) and the two agree; the backup's tests: it restores to the same rows, rotation keeps the newest, a full disk stops it and deletes nothing, five backups taken while another process writes all verify, a damaged database is refused. `pnpm check` is green. *Question: is that enough proof to try the first real press?*
